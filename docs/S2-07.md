## What changed

### One switch for every service

`AppDependencies` (`lib/app_scope.dart`) chooses the services from the
backend URL:

| Service | `JAMSCAN_API_URL` set | Not set (offline demo) |
| --- | --- | --- |
| Photo recognition | `QueuedRecognitionService` → `POST /recognitions` | `MockRecognitionService` |
| Live recognition | `HttpRecognitionApi` | `MockRecognitionApi` |
| Manual search | `HttpCatalogService` → `GET /releases/search` | `MockCatalogService` |
| Release details | `RepositoryReleaseDetails` → `GET /releases/{id}` via the S2-05 cache | `BasicReleaseDetails` |
| Metadata cache | `AppDatabase` (on-device SQLite) | none |

With a backend no mock is used. Without one the app keeps the Sprint 1
mocks, so every screen can still be demonstrated and the widget tests stay
deterministic. A URL without a trailing slash gets one, so a path prefix
(`http://host/api`) is kept.

### Release endpoints (`lib/services/release_api.dart`)

`HttpReleaseApi` calls `GET /releases/{id}` and `GET /releases/search`.
Timeouts (30 s: the backend looks up iTunes previews before it answers),
HTTP errors, network failures and malformed JSON all become a
`ReleaseApiException`. Discogs titles search hits `Artist - Title`; the
artist is split off at the first ` - `.

### Real metadata through the cache

`RepositoryReleaseDetails` (`lib/services/release_details_service.dart`)
uses the `ReleaseRepository` from S2-05: a release fetched in the last week
opens without a request, a stale copy is shown (marked partial) when the
backend is down, and `toViewModel()` gives the screens their `Album`. The
recognition session uses it for live results, and so does the photo flow.

### Candidates and search hits load details on selection

Recognition candidates and search hits carry only artist, title, year,
format and cover. They are listed as *partial* albums. The full details are
loaded only for the one the user picks (`ReleaseDetailsService.complete`):

- **Manual search:** tapping a hit shows the progress bar, loads its
  details, then opens it on the camera page.
- **"Which one is it?" (photo flow):** picking a candidate shows *Loading
  album details*, then the result. Previously the photo flow loaded the
  details of every candidate before showing the list; now unpicked
  candidates cost no requests (Discogs allows 60 requests a minute).
- **Live *Needs review*:** already loaded on selection through
  `RecognitionSession.resolve` (S2-11).

If the details cannot be loaded the partial album is still shown, with the
"Showing saved info" banner on Album Details, so selecting always works.

### Covers

`Album` has a `coverUrl`, filled from the cached Discogs metadata and from
search hits. `AlbumArt` shows the HTTPS image and keeps the grey
placeholder while it loads, when it fails, and for sample albums. That
covers search results, candidate lists, the result card, Album Details,
library rows and history.

### Backend: year and format on search hits

`GET /releases/search` now also returns `year` (Discogs sends it as a
string) and `format` (`Vinyl, LP, Album`). The app shows them in the
results and the Vinyl/CD filter of manual search uses the format; without
it every hit counted as vinyl. Both are `null` when Discogs has no value.
The app still parses responses without the two fields.

## How to run against the backend

1. Start the backend (see [S2-03.md](S2-03.md) for the model and index).
   The token is read from the environment; `.env` is not loaded
   automatically.

   ```powershell
   cd backend
   $env:DISCOGS_TOKEN = "<your personal token>"
   python -m scripts.download_model
   python -m scripts.build_index
   python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
   ```

   For the 5,000-album index, build it as described in
   [LARGE_DATASET.md](LARGE_DATASET.md) and set
   `$env:JAMSCAN_INDEX_DIR = "data/index_5k"` before starting the server.

2. Run the app with the backend URL:

   ```bash
   cd mobile
   flutter run --dart-define=JAMSCAN_API_URL=http://10.0.2.2:8000
   ```

   `10.0.2.2` is the host machine from the Android emulator. On a phone,
   use the laptop's address on the same Wi-Fi. Debug builds allow plain
   HTTP; release builds need an HTTPS backend.

### First run on a phone (15 November 2026)

Setup: backend on a Windows laptop (Python 3.12, DINOv2 model, the
42-album dev index from `fetch_dev_covers` and `build_index`), reached over
Wi-Fi at `http://192.168.1.28:8000`; debug APK built with
`--dart-define=JAMSCAN_API_URL=http://192.168.1.28:8000` and installed on a
Samsung phone. Before the phone test, the laptop itself confirmed `/health`,
a Discogs search with cover, year and format, and a correct match from
`POST /recognitions`.

Requests from the phone, from the backend log:

| Endpoint | Succeeded | Failed |
| --- | --- | --- |
| `POST /recognitions` | 10 | 0 |
| `GET /releases/{id}` (details and previews) | 5 | 0 |
| `GET /releases/search` | 79 | 25 (HTTP 503) |

**Problem found and fixed:** manual search sent a request on every
keystroke. Typing one title used up Discogs' limit of 60 requests a minute,
the backend answered 503, and the app showed "Discogs isn't responding".
The sample catalogue has no limit, so this only showed with the real
service. Manual search now waits until typing pauses (500 ms,
`CatalogService.typingDelay`) before it searches; Enter, retry and clearing
still search at once, and the offline mock still searches as you type.

The full scenario run (live scan, photo, gallery, candidate selection,
previews, backend stopped) with screenshots is part of the S2-08
end-to-end validation.

## Known limitations

- `GET /releases/{id}` does not return the Discogs format, so a fully
  loaded release shows "Vinyl" and no *Format* row in pressing details,
  while its search hit showed the exact format. Adding `format` to
  `get_release` and `ReleaseMetadata` would fix it.
- Country and rating count are not returned by the backend yet (as in
  S2-05).
- Cover images are not downloaded for offline use (`cover_path` stays
  empty); a cached release keeps its cover URL.
- Recognition only knows the albums in the reference index it runs with
  (the 154-album S2-02 list or the 5,000-album list from S2-02b; see
  [LARGE_DATASET.md](LARGE_DATASET.md)).
- The library and history are still the in-memory stores of the UI shell;
  saving to the database is Sprint 3.
