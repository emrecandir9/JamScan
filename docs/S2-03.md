# S2-03: album-cover recognition service

Owner: Emre. Reviewer: Olena. Estimate: 10 SP. Branch: `feature/S2-03-recognition-service`.

> As a user, I want the application to recognize an album cover so that I can
> identify unfamiliar records.

Acceptance criteria: the recognition algorithm processes an image and returns
ranked album candidates with matching scores; recognition accuracy is
evaluated and documented.

Status on **2026-10-19**: first part of the story. The backend recognition
service, the reference-index format, and a 42-album development index are
implemented and tested. Accuracy on real phone photos and threshold
calibration follow once the S2-02 reference dataset exists (branch
`feature/S2-03-recognition-evaluation`).

## How recognition works

```text
upload ─► decode (EXIF upright, RGB) ─► quality check ─► DINOv2-small (ONNX)
       ─► 384-d unit vector ─► cosine vs reference index ─► decision
```

1. **Preprocessing** (`app/recognition/preprocess.py`): the image is decoded,
   turned upright, centre-cropped to a square, resized to 224 × 224 and
   normalised with ImageNet statistics. The phone sends an already cropped,
   flattened cover (S2-10), so the centre crop only matters for raw uploads.
2. **Quality check**: variance of the Laplacian (sharpness) and mean grey
   level (brightness). Blurry, very dark or overexposed photos return
   `poor_quality` without running the model.
3. **Embedding** (`embedder.py`): [DINOv2-small](https://huggingface.co/facebook/dinov2-small)
   (Apache-2.0), run on the CPU with ONNX Runtime. The final class token is
   L2-normalised into a 384-number vector. No PyTorch is needed.
4. **Search** (`index.py`): exact cosine similarity against every reference
   vector. Several photos of one release keep only their best score.
5. **Decision** (`matcher.py`):

   | Decision | Rule (provisional values) | App behaviour |
   | --- | --- | --- |
   | `match` | best ≥ 0.75 and best − second ≥ 0.05 | open the result |
   | `needs_review` | best ≥ 0.60 | "Which one is it?" candidates |
   | `no_match` | best < 0.60 | "We couldn't identify this album" |
   | `poor_quality` | sharpness < 15 or brightness outside 35–235 | retake / use anyway |

   Values can be overridden with environment variables (below) and will be
   calibrated on real photos.

## API contract

`POST /recognitions`, `multipart/form-data`:

| Field | Type | Notes |
| --- | --- | --- |
| `image` | file | JPEG or PNG, at most 10 MB. A 512 × 512 JPEG cover crop is ideal. |
| `skip_quality_check` | bool, optional | `true` for the app's "Use anyway". |

Response `200`:

```json
{
  "decision": "match",
  "candidates": [
    {"release_id": "12643712", "artist": "Fleetwood Mac", "title": "Rumours",
     "year": 1977, "score": 0.8995}
  ],
  "quality": {"sharpness": 72.0, "brightness": 116.1},
  "model_id": "dinov2-small/cls/v1",
  "timings_ms": {"preprocess": 5.8, "embed": 18.6, "search": 0.1}
}
```

- `candidates` are best first and only include scores ≥ the review
  threshold; for `no_match` and `poor_quality` the list is empty.
- `release_id` is the Discogs release ID. Album details, tracks and previews
  come from the S2-04 metadata endpoint, not from this one.
- `score` is cosine similarity clipped to 0–1; the app shows it as "% match".
- Errors: `422` not an image, `413` larger than 10 MB, `503` model or index
  not configured (the rest of the API still runs).

The mobile `RecognitionOutcomeKind` maps directly: `match` → `match`,
`needs_review` → `candidates`, `no_match` → `notRecognised`,
`poor_quality` → `tooBlurry`.

## Reference dataset format (S2-02 handoff)

The dataset is a folder with a `covers.csv` and the images it lists:

```text
my-dataset/
  covers.csv          release_id,artist,title,year,image
  images/7964182.jpg
  images/7964182-2.jpg   (optional: more photos of the same release)
```

- `release_id`: Discogs release ID (required, used by S2-04).
- `image`: path relative to the folder. Square front covers work best; extra
  photos of the same release (other pressings, real photos) improve recall.
- Images are copyrighted cover art: keep them out of Git. `backend/data/` is
  ignored for this reason.

`python -m scripts.build_index --dataset <folder>` embeds every image with
the server's model and writes `data/index/embeddings.npy` and
`data/index/manifest.json`. The manifest records the model and preprocessing
version, and the server refuses an index built with different ones, so the
index must be rebuilt whenever either changes.

## Run it locally

From `backend/` with the virtual environment active:

```bash
python -m scripts.download_model
export DISCOGS_TOKEN=...   # from your local .env
python -m scripts.fetch_dev_covers
python -m scripts.build_index
uvicorn app.main:app --reload
curl -F image=@data/dev/images/12643712.jpg http://127.0.0.1:8000/recognitions
```

- `download_model` fetches the pinned ONNX file (88 MB) into `models/` and
  verifies its SHA-256.
- `fetch_dev_covers` downloads the 42 development covers listed in
  `datasets/dev_albums.csv` (release IDs are pinned there) into `data/dev/`.
- Docker: the image does not contain the model or the index. Mount them:
  `docker run -p 8000:8000 -v "$PWD/models:/app/models:ro" -v "$PWD/data/index:/app/data/index:ro" jamscan-backend`.

| Variable | Default | Meaning |
| --- | --- | --- |
| `JAMSCAN_MODEL_PATH` | `models/dinov2-small.onnx` | ONNX model file |
| `JAMSCAN_INDEX_DIR` | `data/index` | Folder with `embeddings.npy` and `manifest.json` |
| `JAMSCAN_TOP_K` | `5` | Maximum candidates searched |
| `JAMSCAN_MATCH_THRESHOLD` | `0.75` | Minimum score for `match` |
| `JAMSCAN_MATCH_MARGIN` | `0.05` | Required lead over the second candidate |
| `JAMSCAN_REVIEW_THRESHOLD` | `0.60` | Minimum score to show a candidate |

## Validation so far

- Automated tests: `python -m pytest`. The recognition tests use a small fake
  embedder, so CI does not need the model; one extra test runs the real model
  when `models/` and `data/index/` exist locally.
- Endpoint check with the real model on the 42-cover development index
  (MacBook, CPU): about 25 ms per request (embedding about 18 ms). A blurred
  cover and random noise returned `poor_quality`; a text file returned `422`.
- Synthetic smoke test: each development cover was turned into three simulated
  phone photos (perspective tilt, rotation, loose crop, lighting and colour
  change, glare, blur, JPEG compression) at three strengths. All 378 queries
  ranked the correct release first. Correct covers scored a median of 0.87
  (10th percentile 0.77) at the strongest distortion; the closest wrong cover
  scored a median of 0.45 (90th percentile 0.58, maximum 0.68).
- Pooling choice: the class token alone separated correct and wrong covers as
  well as the class token plus mean patch token, at half the size, and both
  were clearly better than the patch mean alone.

These numbers come from distorted copies of the reference images, so they are
optimistic. They show the pipeline works; they are not the accuracy figure
the story requires.

## Accuracy evaluation

`scripts/evaluate_recognition.py` scores a folder of query photos named
`<release_id>__<anything>.jpg`, or simulated phone photos with
`--augment N`. `--holdout N` hides N releases from the index to check that
unknown albums are not matched. It prints JSON with first-answer (top-1) and
top-5 accuracy, the decision split, wrong matches, latency and a threshold
sweep:

```bash
python -m scripts.evaluate_recognition path/to/phone-photos > report.json
python -m scripts.evaluate_recognition --augment 4 --holdout 10
```

Results on **2026-10-19** (42-album development index, CPU):

| Query set | Top-1 | Auto-matched | Needs review (right album listed) | No match / poor quality | Wrong matches | Latency |
| --- | --- | --- | --- | --- | --- | --- |
| Crops from the mobile live pipeline (S2-10), 33 covers | 100 % | 30 | 2 | 1 / 0 | 0 | 22 ms |
| Simulated phone photos, 128 of 32 known albums | 100 % | 115 | 3 | 0 / 10 | 0 | 19 ms |
| Simulated phone photos, 40 of 10 albums not in the index | — | 0 | 1 | 38 / 1 | 0 | 19 ms |

- In the first row, each crop went through the whole phone pipeline:
  simulated camera frame (YUV, sensor turned 90°), detection, tracking,
  best-frame choice, and flattening to an upright crop. Then it went through
  this endpoint.
- Correct albums scored a median of 0.87–0.89 (10th percentile 0.77–0.81).
  The best wrong album scored a median of about 0.45, and at most 0.66
  across both sets.
- Threshold sweep: a match threshold of 0.70 would auto-match three more
  photos with no wrong matches, but leaves little room above the highest
  wrong score (0.66). The default stays at 0.75 until real photos are
  measured.
- Evidence: [live pipeline](evidence/S2-03-eval-live-pipeline.json),
  [simulated photos with held-out albums](evidence/S2-03-eval-augmented-holdout.json).

All query sets are derived from the reference images, so these results are
an upper bound. The PoC target (more than ⅔ correct) has to be confirmed
with real phone photos of physical records.
