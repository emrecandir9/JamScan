### Useful validated fields

| Provider / response | Fields | Intended use in JamSCAN |
| --- | --- | --- |
| Discogs identity | `id`, `username` | Confirm token authentication only; omit account details from reports. |
| Discogs search | `pagination`, `results[].id`, `.title`, `.type` | List release candidates and select an ID for release lookup. |
| Discogs release | `id`, `title`, `artists[].name` | Identify and label the physical release on its detail page. |
| Discogs release | `tracklist[].title` | Display tracks and form candidate iTunes searches with the artist name. |
| iTunes search | `resultCount`, `results[]` | Distinguish available candidates from an empty search result. |
| iTunes song | `trackId`, `wrapperType`, `kind` | Identify the digital track and confirm that the result is a song. |
| iTunes song | `trackName`, `artistName`, `collectionName` | Compare candidate recording and album labels against Discogs metadata. |
| iTunes song | `trackViewUrl` | Supply the store destination for the preview's purchase link. |
| iTunes song | `previewUrl` (optional) | Stream a supported HTTPS preview when available; otherwise show unavailable. |

These fields are covered by the current probes. Other metadata is outside the
validated contract and should be checked before a feature depends on it.

## Run the checks

Use the Python 3.12 backend development environment from [SETUP.md](SETUP.md).
The tool uses the already locked development dependency `httpx`; dependencies
and production packaging do not change. Run from the source checkout's
`backend/` directory with the virtual environment activated:

```bash
python -m scripts.validate_apis --provider itunes
python -m scripts.validate_apis --provider discogs
python -m scripts.validate_apis
```

The default run checks both providers. Without a Discogs token it still checks
public release `1`, but marks authentication and search `blocked` and exits `1`.
With a token it checks identity, searches for releases, and fetches the first
returned release. A failed authenticated request stops the Discogs sequence.
iTunes is checked independently even if Discogs fails.

The default sample queries are `Daft Punk Random Access Memories` for Discogs
and `Daft Punk Get Lucky` for iTunes. The test storefront defaults to France;
this is configurable and does not set a production market:

```bash
python -m scripts.validate_apis --provider itunes --country US --track-query "Jack Johnson Upside Down"
python -m scripts.validate_apis --provider discogs --query "Daft Punk Discovery"
python -m scripts.validate_apis > api-validation-report.json
```

Each JSON report contains UTC time, query inputs, check outcomes, HTTP status,
elapsed time, numeric rate-limit headers, and selected counts/IDs. Provider
response bodies, credentials, identity details, and preview URLs are omitted.
Exit `0` means every check for the selected provider(s) passed. Exit `1` includes
failures, missing credentials, empty results, or unavailable HTTPS previews;
exit `2` indicates invalid command-line arguments. Search matches are candidates,
not a verified match between a physical release and a digital recording.

### Configure Discogs authentication

1. Sign in to [Discogs developer settings](https://www.discogs.com/settings/developers)
   and generate a personal access token for this development check.
2. Copy `backend/.env.example` to `backend/.env` and fill `DISCOGS_TOKEN` locally.
   `.env` is ignored by Git. Do not put the token in Dart, reports, or chat.
3. Export the variable before running the script. The script does not load
   `.env` automatically. For a locally authored `.env`, on macOS/Linux:

```bash
set -a
source .env
set +a
python -m scripts.validate_apis --provider discogs
```

On Windows, set `DISCOGS_TOKEN` in the process environment using your local
environment/secret tooling, then run the same Python command.

### How to tell it works

From the repository root, with your token already saved in `backend/.env`:

```bash
cd backend
source .venv/bin/activate
set -a
source .env
set +a
python -m scripts.validate_apis
echo "Exit code: $?"
```

Success means `Exit code: 0` and **five** report entries with `"status": "passed"`:
`discogs.authentication`, `discogs.search`, `discogs.release`, `itunes.search`,
and `itunes.preview`. The first four should report HTTP `200`; the preview
accepts `200` or `206` and should report a positive `bytes_sampled` count.
If a check is blocked, failed, or inconclusive, read its `detail` field; the
command exits `1`. A missing token indicates that `.env` was not populated or
exported; an authentication rejection means the token needs checking.

This story is verified in the terminal. The mobile welcome screen does not
change, and this command does not play audio through your speakers. It checks
that the services respond correctly and that preview audio can be received.

The script uses `Authorization: Discogs token=...` and a JamSCAN `User-Agent`.
Personal-token auth is appropriate for this development probe; user-account
integration may later require OAuth. See the
[Discogs-owned authentication guide](https://github.com/discogs/discogs_client/blob/master/docs/authentication.md)
and [User-Agent guidance](https://github.com/discogs/discogs_client/blob/master/docs/quickstart.md).
That client repository is archived; this tool uses direct HTTP, not its SDK.

## Contracts and limitations

| API/check | Request and expected response | Authentication and limits |
| --- | --- | --- |
| Discogs identity | `GET https://api.discogs.com/oauth/identity`; JSON `id` and `username`. Account fields are checked, then omitted from the report. | Personal token required; authenticated request passed. |
| Discogs search | `GET /database/search` with `q`, `type=release`, `per_page=3`, `page=1`; JSON `pagination` and `results[]` with `id`, `title`, `type`. | Authenticated request passed. Empty results are inconclusive. |
| Discogs release | `GET /releases/{id}`; JSON matching `id`, `title`, `artists[].name`, `tracklist[].title`. | Public release `1` works without a token. Capture `X-Discogs-Ratelimit`, `-Used`, and `-Remaining` rather than assuming capacity. |
| iTunes search | `GET https://itunes.apple.com/search` with `term`, `country`, `media=music`, `entity=song`, `limit=5`; JSON `resultCount` and `results[]`. | No credentials. Apple documents approximately 20 calls/minute, subject to change. |
| iTunes preview | Use a returned HTTPS `previewUrl` on an Apple media host; range request for bytes `0–1023`, accepting HTTP `200`/`206` and nonempty `audio/*`. | No credentials. Samples stay in memory; audio is never saved. Redirects and unsupported hosts are reported rather than followed. |

iTunes song fields checked are `trackId`, `wrapperType=track`, `kind=song`,
`trackName`, `artistName`, `collectionName`, and `trackViewUrl`. `previewUrl`
is optional. A missing or non-HTTPS preview produces an inconclusive result,
not a false availability claim. Storefront, recording version, and catalog
changes can affect matching and availability. `trackTimeMillis` describes
the song, not the preview duration; this probe does not infer preview length.
See Apple's [search parameters and limits](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/Searching.html)
and [response fields](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/UnderstandingSearchResults.html).

Every request has a 15-second HTTPX timeout (per network operation), no automatic
retries, and no redirect following. HTTP errors, invalid JSON, and unexpected
response shapes fail the check. Numeric `Retry-After` seconds are recorded for
JSON requests; date-form headers are not retained. Do not repeatedly rerun a
rate-limited request. These checks do not load-test the providers or deliberately
exhaust quotas. A production client will need throttling and backoff.

The current Discogs developer documentation returned HTTP 403 during research.
Live responses reported capacities of **25 without authentication** and
**60 with authentication**. The authenticated sequence reported used/remaining
values of `0/60`, `1/59`, and `2/58`. These are observed headers, not a measured
rate window or a quota guarantee. Consult the
[Discogs API documentation](https://www.discogs.com/developers/)
for the current window and policy. No quota-exhaustion test was performed.
