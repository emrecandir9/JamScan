## 1. Objective

Integrate the JamSCAN FastAPI backend with external music services so that recognized albums can display real metadata and available audio-preview links.

The implementation provides reusable Discogs and iTunes services, REST endpoints for album search and details, and controlled handling of external API failures. Integration with the visual recognition algorithm developed in S2-03 is a remaining dependency.

## 2. Work Completed

### 2.1 Discogs API Integration

Implemented `app/services/discogs.py` to retrieve music-release metadata and perform manual album searches through the Discogs API.

The service provides two main functions:

- `search_releases()`: Searches the Discogs database using a text query and returns candidate releases with Discogs identifiers, titles and cover URLs.
- `get_release()`: Retrieves and normalizes release metadata, including artist, album title, release year, artwork, label, catalogue number, genres, styles, rating and tracklist.

Discogs authentication uses the `DISCOGS_TOKEN` environment variable. Credentials are not stored in application source code.

The implementation handles invalid responses, unavailable releases, authentication errors, rate limits and network timeouts through controlled exceptions.

### 2.2 iTunes Preview Integration

Implemented `app/services/itunes.py` to retrieve available music-preview URLs through the iTunes Search API.

The service searches for songs using their artist and track titles, validates matching results and extracts available HTTPS preview URLs and Apple Music store links.

The matching logic supports collaborative artist credits while avoiding unrelated artists or recordings. When possible, results from the corresponding album are preferred.

Tracks without a suitable preview remain available in the metadata response without a playable URL.

### 2.3 FastAPI Endpoints

Implemented the following REST endpoints:

**`GET /releases/search`**

Accepts a text query and returns matching Discogs release candidates. This endpoint supports the manual-search fallback when image recognition is unsuccessful.

**`GET /releases/{release_id}`**

Accepts a Discogs release identifier and retrieves the corresponding album metadata, enriched with available iTunes preview links.

The complete Discogs tracklist is preserved. To limit external API requests, the initial implementation attempts preview retrieval for at most five tracks per request.

The response includes `preview_status`, `previews_checked`, `previews_available` and `preview_lookup_limit` fields.

The existing `GET /health` endpoint remains available.

## 3. Error Handling

External API failures are handled without exposing credentials or raw provider diagnostics.

Discogs failures produce controlled HTTP errors with appropriate status codes.

If iTunes is unavailable, the backend preserves the album metadata and reports preview availability separately. Missing track previews do not cause album retrieval to fail.

Invalid requests, missing releases, timeouts, rate limits and malformed provider responses are covered by automated tests.

## 4. Recognition Integration

The visual recognition algorithm is developed separately under S2-03 by Emre.

The shared recognition API uses `POST /recognitions` and returns ranked Discogs release candidates. The release identifiers can subsequently be used with `GET /releases/{release_id}` to retrieve album details and available previews.

A temporary recognition upload endpoint was initially implemented during S2-04 development but subsequently removed to avoid duplicating the S2-03 implementation.

Final registration of both API routers in the same FastAPI application remains pending the integration of S2-03 into the shared main branch.

## 6. Dependencies and Configuration

Runtime dependencies include FastAPI, Uvicorn and HTTPX. Dependency versions are maintained through the project's Python dependency lock files.

Discogs requests require a personal access token configured through `DISCOGS_TOKEN`. iTunes Search API requests do not require authentication.

The implementation follows the repository's existing Python conventions and preserves the separation between external API services, FastAPI routes and the recognition component.
