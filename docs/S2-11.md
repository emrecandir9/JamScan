# S2-11: recognition job queue and live results

Owner: Emre. Branch: `feature/S2-11-recognition-job-queue` (built on S2-10).

> As a user, I want several albums to be recognised while I keep scanning,
> and to find the results on the camera page.

Requirements covered: FR-05 (status display), FR-06 (three active jobs),
FR-07 (waiting queue), FR-08 (continues after the album leaves the view),
FR-09 and FR-10 (results reachable from the scan page until dismissed),
FR-11 (manual capture remains available), FR-12 (candidate selection), and
manual-capture priority (§4.4.4). Status on **2026-10-19**: implemented,
tested, and run end to end on the Android emulator against the real
recognition backend.

## How it works

- **`RecognitionSession`** (`state/recognition_session.dart`) holds one
  job per album. The states follow §4.4.3: *Queued → Processing →
  Identifying → Retrieving details → Done*, or *Needs review* / *Failed*
  (not identified, unclear photo, service unavailable). *Detected* belongs
  to covers that are tracked but not yet captured, so the panel takes it
  from the live scanner.
  - At most three jobs hold a slot (processing, identifying or retrieving
    details); the rest wait. Manual requests are served before queued live
    ones; otherwise first come, first served.
  - A job only needs its captured crop, so it continues after the cover
    leaves the camera view.
  - Finished jobs free their slot and stay until dismissed or the app
    closes. Opening Album Details does not reset them.
  - The same album is not recognised twice. A live crop within 10 bits
    (difference hash) of an earlier one is ignored (failed jobs excepted, so
    a cover can be retried). A second *Done* result for an album already
    found is dropped.
- **`HttpRecognitionApi`** (`services/recognition_api.dart`) sends the crop
  to `POST /recognitions` (S2-03), with a 15 s timeout. Server errors, bad
  responses and network failures all become *service unavailable*.
- **`QueuedRecognitionService`** puts manual photos and gallery imports
  through the same queue, after preparing them in a background isolate
  (S2-10 still-photo path). It keeps the existing *Identifying album →
  result* screens and maps backend decisions to their outcomes.
- **`ReleaseDetailsService`** turns a recognised release into an `Album`.
  `BasicReleaseDetails` uses the sample catalogue or the recognition data
  (marked partial) until the Discogs metadata endpoint (S2-04) provides
  full details.
- **`LiveResultsPanel`** (`widgets/live_results_panel.dart`): one
  horizontal strip of compact chips in its own band above the guide square,
  newest first, scrolling sideways when full. The band is kept while empty,
  so the square never moves and no album being framed is covered; several
  detected covers share one chip. *Done* cards show the captured crop,
  title and artist and open Album Details; *Needs review* opens a candidate
  list with "None of these – search manually". This layout is functional;
  visual design is part of the UI work.

### Configuration

The backend URL is a build-time setting:

```bash
flutter run --dart-define=JAMSCAN_API_URL=http://10.0.2.2:8000
```

`10.0.2.2` is the host machine as seen from the Android emulator; on a
phone, use the laptop's address on the same Wi-Fi. Without the setting the
app keeps its offline mocks, as in Sprint 1. Switching the default is part
of S2-07. Debug builds allow plain HTTP for this; release builds keep
Android's HTTPS-only default. The main manifest now requests `INTERNET`,
which release builds need to reach any backend.

### End to end on the Android emulator

Setup: Pixel 9 emulator (Android, CameraX), back camera fed a picture of a
table (`emulator -camera-back imagefile:scene.png`). The S2-03 backend ran
on the Mac with the DINOv2 model and the 42-album dev index, and the app was
built with `JAMSCAN_API_URL=http://10.0.2.2:8010`.

| Scenario | Result |
| --- | --- |
| One cover (Rumours) | outlined live, captured automatically after a few frames, recognised; card *Rumours · Fleetwood Mac · Done*; one upload while the cover stayed in view |
| Card tapped | Album Details for Rumours (partial details until S2-04) |
| Manual shutter | photo taken with the live camera, *Identifying album…* screen, *Match found: Rumours*; the live card was still listed |

### Fixed after a full flow run (2026-10-19)

A screenshot run from a fresh install found four problems, now fixed and
covered by tests:

1. **Camera did not start after the permission prompt.** The prompt pauses
   the app mid-start, and the pause's stop closed the camera after it
   opened. Start and stop now only set whether the camera should run; one
   serialized loop opens or closes it until it matches. After a refusal,
   the app asks again only from "Allow camera access".
2. **An unknown album was resent** each time the camera re-acquired it
   (after visiting Album Details). Only failures that a retry can fix
   (service unavailable, unclear photo) now allow a resend.
3. **A dismissed card came back** when the camera saw the cover again. The
   session remembers dismissed covers until it ends.
4. **Partial albums showed "0" for an unknown year**, a dangling "·" and
   empty rows on Album Details. Unknown values are now left out, and an
   empty tracklist reads "No tracklist yet".

Also, the live panel is hidden while a photo's result card is open, and two
timing-sensitive tests now wait for conditions instead of fixed delays.

5. **The results panel covered albums.** It sat in the top-right of the
   camera view, over the guide square. It is now a strip above the square
   (a widget test checks the strip ends above the square and the square
   does not move), and failure labels are shorter so the dismiss button
   stays on screen on a 360-point-wide phone.

## Known limitations

- With more than two results, the strip needs a sideways swipe to show the
  rest. Once during testing the strip came up empty after a swipe; three
  repeats did not reproduce it.
- No retry button yet for *service unavailable*; a new capture of the same
  cover is accepted after a failure.
- Not yet tried on a physical phone or with a backend reached over Wi-Fi.
