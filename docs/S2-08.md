# S2-08: End-to-end workflow validation

Owner: Olena. Reviewer: Entire team. Estimate: 3 SP. Branch: `feature/S2-08-e2e-validation`.

> As a team, we want to validate the complete recognition workflow so that
> the main functionality works reliably.

Acceptance criteria: a reproducible test covers capture/import →
recognition → Album Details → playback, including failure paths for no
recognition match, unavailable API, and missing preview.

The validation has two parts: automated end-to-end tests that anyone can
rerun, and a manual run on a real phone against the real backend.

## 1. Automated end-to-end tests

`mobile/test/e2e/workflow_test.dart` starts the whole app and walks through
it like a user. Only the edges are fake: the camera and gallery, the
recognition endpoint (`POST /recognitions`), the release endpoints
(`GET /releases/...`) and the audio engine. Everything in between is the
real code: the photo flow, `QueuedRecognitionService`, `RecognitionSession`,
the S2-05 metadata cache, the S2-07 release services, Album Details and the
S2-06 preview player.

| ID | Scenario | Checked |
| --- | --- | --- |
| E2E-1 | Camera photo, confident match | Result card, Album Details with Discogs metadata (label, catalogue number, tracklist), preview plays with the 30 s limit, mini player, track without preview disabled |
| E2E-2 | Gallery import, confident match | Same result and details as a camera photo |
| E2E-3 | Ranked candidates | "Which one is it?" lists both; release details are requested only for the album picked |
| E2E-4 | No match | "We couldn't identify this album", manual search finds and opens the album |
| E2E-5 | Recognition backend unavailable | No crash; search manually and retake are offered (see defect D1) |
| E2E-6 | Metadata backend unavailable | Album still opens from recognition data, marked "Showing saved info" |
| E2E-7 | Album without previews | "No previews available for this album.", every play button disabled, no audio loaded |

To make the photo flow testable, `QueuedRecognitionService` accepts an
optional `readPhoto` function (default: reading the file). Real file I/O
does not complete inside widget tests; the app behaviour is unchanged.

Run from `mobile/`:

```bash
flutter test test/e2e/workflow_test.dart
```

Result: 7 of 7 pass; the full suite passes (178 tests, 1 skipped) and
`flutter analyze` reports no issues.

## 2. Manual test on a real device

Setup: POCO F7 (Android 15) running a debug build, backend on a Windows
laptop with the 5,000-album index (`JAMSCAN_INDEX_DIR=data/index_5k`),
connected through `adb reverse tcp:8000 tcp:8000`, real Discogs and iTunes
services. Covers were photographed from a laptop screen and imported from
the phone gallery.

Albums used: Pink Floyd, *The Dark Side Of The Moon*; Fleetwood Mac,
*Rumours*; The Beatles, *Abbey Road*; Nirvana, *Nevermind* (cover images
shown on a laptop screen and saved to the phone gallery).

| ID | Scenario | Result | Notes |
| --- | --- | --- | --- |
| M-1 | Camera photo of a cover in the dataset | Pass | Correct album, a few seconds from shutter to result |
| M-2 | Album Details | Pass | Label, catalogue number, genres, tracklist and cover shown |
| M-3 | Preview playback | Pass | Plays and stops after 30 s, mini player shown |
| M-4 | Gallery import | Pass | Same result as a camera photo |
| M-5 | Cover not in the dataset | Pass | "We couldn't identify this album", manual search works |
| M-6 | Similar covers or a difficult angle | Pass | Some photos matched directly, others asked to confirm ("Which one is it?"); picking a candidate opened its details |
| M-7 | Scanning an album again | Pass | Opened from the local cache |
| M-8 | Backend stopped | Not tested | Covered by automated test E2E-5 |
| M-9 | Tracks without a preview | Pass | Play button disabled for those tracks |
| M-10 | Blurry or dark photo | Pass | "Photo too blurry or dark" with retake and use anyway |
| Extra | Live camera recognition (S2-09 to S2-11) | Partial | Usually found the cover on its own; sometimes it did not trigger, and taking a photo then identified the album |

Screenshots: `docs/evidence/S2-08/`.

## 3. Defects and observations

| ID | Type | Description | Suggested action |
| --- | --- | --- | --- |
| D1 | Defect | When the recognition backend cannot be reached, the photo flow shows "We couldn't identify this album", the same message as an album that is not in the dataset. `RecognitionSession` records the failure as `unavailable`, but `QueuedRecognitionService` reports every failure except poor quality as not recognised. The fallbacks (search, retake) still work. | Add an "unavailable" outcome with a message such as "Recognition is unavailable, check your connection" and a retry button. Sprint 3 backlog. |
| O1 | Observation | Live camera detection sometimes does not trigger on a cover held in view, while a photo of the same cover is identified. | Collect examples (lighting, angle, screen versus record) and review the detection thresholds with the S2-09 owner. |
| O2 | Observation | Recognition confidence varies with the photo: the same album is sometimes matched directly and sometimes offered as a candidate. This is the intended behaviour (unsure results ask the user rather than guess). | Re-check with the S2-03 accuracy evaluation on real phone photos. |
| O3 | Setup | On Windows, the Android build fails with Kotlin "different roots" errors when the project and the Flutter package cache are on different drives (for example `D:` and `C:`). | Set `PUB_CACHE` to the project's drive; add the tip to `docs/SETUP.md`. |
| O4 | Setup | The app only works while the backend runs on a laptop on the same network (or through `adb reverse`). | Deploy the backend (Dockerfile exists) to a cloud host for the final demo. Sprint 3 or 4 backlog. |

## 4. How to repeat the manual test

1. Start the backend from `backend/` with `DISCOGS_TOKEN` and
   `JAMSCAN_INDEX_DIR=data/index_5k` set:
   `python -m uvicorn app.main:app --host 0.0.0.0 --port 8000`
2. Connect the phone with USB debugging on and run
   `adb reverse tcp:8000 tcp:8000`.
3. From `mobile/`:
   `flutter run -d <device id> --dart-define=JAMSCAN_API_URL=http://localhost:8000`
4. Go through M-1 to M-10 above.
